## Objetivo

Quando um roteador OpenAI-compatível (OpenRouter `auto`, aliases do LiteLLM, gateways locais) ou o backend Codex informa no stream qual modelo de fato atendeu, o evento de uso persistido na sessão (`provider_usage`) passa a ter a chave opcional `resolvedModel` com esse valor, **limpo** (texto não confiável) e **só quando difere do modelo pedido**. `model` e o preço não mudam. O `zero usage report` (texto e `--json`) mostra esse valor só quando ele difere do pedido, limpo também na leitura (R10, commit separado).

## Risco

**Alto.** O valor vem de um servidor de terceiros e é gravado em disco e lido por terminais e ferramentas; um erro aqui deixa um gateway injetar sequências de terminal ou texto bidi no histórico do usuário.

## Contrato

### Funções novas: `internal/zeroruntime/resolved_model.go`

```go
// MaxResolvedModelBytes caps the stored provider-reported model id.
const MaxResolvedModelBytes = 256

// SanitizeResolvedModel returns raw as safe, bounded, printable text.
func SanitizeResolvedModel(raw string) string

// ResolvedModelAttribution returns the sanitized reported model, or "" when it
// is empty after sanitizing or equals the sanitized requested model.
func ResolvedModelAttribution(requested, reported string) string
```

`SanitizeResolvedModel(raw)`, nesta ordem:
1. Percorre `raw` runa a runa (`utf8.DecodeRuneInString`). Descarta byte UTF-8 inválido (`RuneError` com tamanho 1). Mantém a runa só se `unicode.IsPrint(r)` for verdadeiro. Isso remove, entre outros: C0 (`U+0000`–`U+001F`), DEL (`U+007F`), C1 (`U+0080`–`U+009F`), todos os `Cf` (bidi `U+202A`–`U+202E` e `U+2066`–`U+2069`, `U+200B`–`U+200F`, BOM `U+FEFF`, hífen suave `U+00AD`), `U+2028`/`U+2029`, espaços não ASCII (`U+00A0`, `U+3000`), uso privado e não atribuídos. `U+FFFD` é imprimível e fica.
2. `strings.TrimSpace` (depois do passo 1, o único espaço possível é o ASCII `U+0020`).
3. Se passar de `MaxResolvedModelBytes` bytes, corta no maior prefixo de no máximo 256 bytes que termina numa fronteira de runa. Sem reticências nem marcador.
4. `strings.TrimRight(s, " ")` (o corte pode deixar espaço no fim).

Propriedades: o resultado é UTF-8 válido, tem no máximo 256 bytes, só contém runas com `unicode.IsPrint`, não começa nem termina com espaço, e `SanitizeResolvedModel(SanitizeResolvedModel(x)) == SanitizeResolvedModel(x)`. Remove caracteres, não sequências: `"\x1b[31mevil\x1b[0m"` vira `"[31mevil[0m"` (texto inofensivo).

`ResolvedModelAttribution(requested, reported)`: `r := SanitizeResolvedModel(reported)`; se `r == ""` ou `r == SanitizeResolvedModel(requested)`, devolve `""`; senão devolve `r`. Igualdade exata de bytes, sensível a maiúsculas. Os dois lados passam pela mesma limpeza **antes** da comparação ("normalize before matching", AGENTS.md).

### Provedor OpenAI-compatível (`internal/providers/openai/provider.go`, `emitChunk`)

- Em cada chunk decodificado (com ou sem `usage`): `if m := zeroruntime.SanitizeResolvedModel(chunk.Model); m != "" { state.resolvedModel = m }`. Um `model` que fica vazio depois da limpeza não apaga um valor anterior.
- No chunk com `usage`: o `StreamEventUsage` leva `ResolvedModel: zeroruntime.ResolvedModelAttribution(provider.model, state.resolvedModel)`. `provider.model` é o mesmo valor enviado no corpo do pedido (`chatCompletionRequest.Model`).
- Os outros campos do `Usage` não mudam.

### Provedor Codex (`internal/providers/openai/codex_responses.go`, `handleTerminalResponse`)

- Quando `event.Response.Usage != nil`: `usage.ResolvedModel = zeroruntime.ResolvedModelAttribution(p.inner.model, event.Response.Model)`, antes do `SendEvent`. Vale para `response.completed` e `response.failed` (o uso é emitido antes do erro, como hoje). O mesmo código atende o transporte HTTP/SSE e o WebSocket (`codex_session.go` chama `emitParsedResponsesEvent`, que chega a `handleTerminalResponse`).
- `response.model` de eventos não terminais (`response.created`, `response.in_progress`) é ignorado.

### Agregação (`internal/zeroruntime/helpers.go`, `mergeUsageSnapshot`)

Como no fork: `resolvedModel := left.ResolvedModel; if right.ResolvedModel != "" { resolvedModel = right.ResolvedModel }`, aplicado no resultado normal e no caminho de erro de `NormalizeUsage`.

### Gravação (`internal/usage/report.go`, `EventUsagePayload`)

`if m := zeroruntime.SanitizeResolvedModel(u.ResolvedModel); m != "" { payload["resolvedModel"] = m }`. Não compara com o modelo pedido (o gravador não o conhece; isso é do provedor). Nenhuma outra chave muda; `model` continua sendo acrescentado depois, só nas execuções com escalonamento, pelos chamadores (`internal/cli/exec.go`, `internal/tui/model.go`).

### Exibição no relatório (R10, commit separado): `internal/usage/report.go` e `internal/cli/usage.go`

**Tipo e campo novos (`internal/usage/report.go`):**

```go
// ResolvedModelUsage aggregates usage events whose provider reported a model
// different from the requested one. Attribution only: cost stays with the
// requested model.
type ResolvedModelUsage struct {
	RequestedModel string `json:"requestedModel"`
	ResolvedModel  string `json:"resolvedModel"`
	Requests       int    `json:"requests"`
	TotalTokens    int    `json:"totalTokens"`
}

// Report ganha, depois de CostEstimated:
	ResolvedModels []ResolvedModelUsage `json:"resolvedModels,omitempty"`
```

**Agregação (`BuildReport`), no laço de eventos:**
1. Calcule o modelo pedido **uma vez**, com a precedência do preço: `requested := payload.Model`; se vazio, `modelBySession[event.SessionID]`. O preço passa a usar essa mesma variável (hoje é `modelID`; só muda de lugar).
2. Logo depois de somar os tokens no bucket e no total, e **antes** dos `continue` do bloco de preço (`modelID == ""`, `registry == nil`, `registry.Require` com erro, `CalculateCost` com erro): `if r := zeroruntime.ResolvedModelAttribution(requested, payload.ResolvedModel); r != "" { acumula na chave {zeroruntime.SanitizeResolvedModel(requested), r}: Requests++, TotalTokens += payload.TotalTokens }`. Um roteador como `router/auto` não tem preço no registro; se a agregação ficar depois dos `continue`, o caso principal some do relatório.
3. Depois do laço: se o mapa está vazio, `report.ResolvedModels` fica `nil` (a chave some do JSON pelo `omitempty`, que omite slice vazio ou nil). Senão, vira slice ordenado por `RequestedModel` e depois `ResolvedModel`, comparação de bytes (`sort.Slice` com chave total; o mapa não tem ordem).

A limpeza na leitura é a mesma da gravação (`SanitizeResolvedModel` e `ResolvedModelAttribution`, sem função nova). Ela existe porque o `events.jsonl` pode ter `resolvedModel` cru, gravado por um build anterior do fork, ou igual ao pedido (o fork gravava sempre). Os dois lados passam pela limpeza antes da comparação (D-2.1-c). O valor `requestedModel` mostrado também é o limpo. Nenhum custo por modelo resolvido (R4): `TotalCost`, `Buckets` e `Total` não mudam.

**Texto (`FormatReport`):** depois da linha `total` e antes da linha em branco de `net LOC`, só quando `len(report.ResolvedModels) > 0`:

```go
builder.WriteString("\nresolved models (reported by provider; cost uses the requested model)\n")
for _, m := range report.ResolvedModels {
	requested := m.RequestedModel
	if requested == "" {
		requested = "(unknown)"
	}
	fmt.Fprintf(&builder, "  requests %d, tokens %s: %s -> %s\n",
		m.Requests, groupThousands(m.TotalTokens), requested, m.ResolvedModel)
}
```

Exemplo (os valores da linha `total` são ilustrativos):

```
total                 4          6,000          $0.03

resolved models (reported by provider; cost uses the requested model)
  requests 2, tokens 3,000: gpt-test -> deepseek/deepseek-r1:free
  requests 1, tokens 1,500: gpt-test -> x/y

net LOC (estimate): +0 / -0 = 0
```

- A tabela por dia **não ganha coluna**. Linhas mistas (eventos com e sem atribuição) somam no bucket e no total como hoje; o bloco lista só os pares com atribuição, então a soma das `requests` do bloco pode ser menor que o total.
- Os números vêm primeiro e os valores não confiáveis por último, sem preenchimento: com até 256 bytes, espaços internos e caracteres largos (CJK), um `%-Ns` desalinharia a linha.
- Sem nenhum par, a saída de texto é **byte a byte** a de hoje e o JSON não tem a chave `resolvedModels`.

**Compatibilidade dos consumidores.** O `zero-bridge`, o `zero-bridge-desktop` e o `keen-platypus` leem o JSON do relatório por chave (informado pelo operador; não testado neste desenho). Uma chave opcional nova, fora de `total` e de `buckets`, é aditiva: nenhuma chave existente muda de nome, tipo ou valor. No texto, um consumidor que leia por posição de linha veria o bloco novo só quando há atribuição; quem consome deve usar `--json`. O ACP não muda (não leva uso; ver abaixo).

### Comportamento observável de fora

- Arquivo de eventos da sessão: `$XDG_DATA_HOME/zero/sessions/<sessionId>/events.jsonl` (sem `XDG_DATA_HOME`: `$HOME/.local/share/zero/sessions/...`). Cada uso é uma linha com `"type":"provider_usage"` e `payload` com `promptTokens`, `completionTokens`, `totalTokens`, as chaves opcionais de cache e raciocínio e, agora, `resolvedModel` (opcional, string).
- Quem grava esse evento: `zero exec`, a TUI e o `zero acp` (todos por `usage.EventUsagePayload`). O resultado de `session/prompt` do ACP e as notificações `session/update` **não** carregam uso (medido pelo PM no upstream); a saída `--output-format stream-json` do `zero exec` também não (campos explícitos em `internal/cli/exec_writer.go`) e continua sem `resolvedModel`.
- `zero usage report` e `zero usage report --json`: buckets por dia, totais e custo como hoje (o custo continua vindo de `payload.model`, no escalonamento, ou do modelo da sessão) e, com o commit da exibição, o bloco `resolved models` e a chave `resolvedModels`, só quando algum evento tem atribuição depois da limpeza na leitura. Valem os filtros que o relatório já tem (`--session`, `--since`, `--days`), porque a agregação usa os mesmos eventos.

## Modelo de dados

- Payload do evento `provider_usage`: chave nova opcional `resolvedModel` (string, até 256 bytes, só runas imprimíveis). Ausente quando o provedor não informa o modelo, quando ele é igual ao pedido ou quando fica vazio depois da limpeza.
- Compatível nos dois sentidos: leitores antigos ignoram a chave; payloads antigos decodificam com `ResolvedModel == ""`.
- Sem migração. Sessões gravadas por builds antigos do fork podem ter `resolvedModel` cru ou igual ao pedido; o relatório limpa e compara na leitura (R10), e o arquivo não é reescrito.
- Saída JSON do relatório: chave nova opcional `resolvedModels` (lista de `{requestedModel, resolvedModel, requests, totalTokens}`), ausente quando não há atribuição.

## Especificação para o TDD do dev

Todos os testes ficam ao lado do código (`foo_test.go` junto de `foo.go`), sem rede real (só `httptest`), sem relógio real e sem ler nem gravar o diretório real do usuário. Nos testes que tocam sessões, use `t.TempDir()` para o diretório das sessões e, se o código resolver diretórios do usuário, redirecione `HOME`, `XDG_DATA_HOME`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME` (e, no Windows, `APPDATA`/`LOCALAPPDATA`) com `t.Setenv`. Nenhum teste aqui depende de plataforma, mas eles rodam nos três sistemas; não compare caminhos crus.

Como escrever os valores: no Go, `"\x1b"`, `"\u202e"` e afins; dentro de JSON de SSE, use os escapes JSON (`\u001b`, `\u0000`), porque o decodificador JSON do Go rejeita um byte de controle cru dentro de string (`invalid character '\x1b' in string`, conferido com go1.27.2; o `go.mod` pede go 1.26.11). C1 e caracteres de formato são JSON válido também crus em UTF-8: teste os dois jeitos.

**Nos arquivos `.go`, escreva sempre o escape (`"\u202e"`, `"\ufeff"`, `"\x1b"`), nunca o caractere literal.** Um caractere invisível literal no fonte não se vê na revisão, e o compilador recusa um BOM literal no meio do arquivo (`invalid BOM in the middle of the file`). Algumas ferramentas de edição convertem `\uXXXX` em caractere literal ao gravar: confira o diff com `git diff | grep -nP '[\x{80}-\x{9f}\x{200b}-\x{200f}\x{202a}-\x{202e}\x{2066}-\x{2069}\x{feff}\x{ad}]'` (deve sair vazio).

## Riscos e pontos de atenção

- **Comparar antes de limpar.** É o erro mais provável: comparar `chunk.Model` cru com `provider.model` e só depois limpar. D2.1-8, D2.1-11 e A2.1-6 pegam isso.
- **Limpar só num lugar.** A limpeza fica no provedor (com a comparação) e de novo no `EventUsagePayload`. Um provedor futuro que preencha `ResolvedModel` sem passar por `ResolvedModelAttribution` ainda grava texto limpo, mas pode gravar um valor igual ao pedido; a revisão de provedores futuros deve exigir `ResolvedModelAttribution`.
- **Modelos datados contam como diferentes.** OpenAI e Codex costumam ecoar o nome com data (`gpt-5` → `gpt-5-2025-08-07`). Pela regra literal do mantenedor (omitir só quando igual), esses casos gravam `resolvedModel`. É esperado; não normalize sufixos.
- **Valor gigante.** O leitor SSE aceita linhas de até 16 MiB (`providerio.maxSSELineBytes`), então a limpeza percorre até 16 MiB uma vez por chunk com `model`. É linear e aloca no máximo o tamanho da entrada antes do corte; não guarde o valor cru no estado.
- **Vários chunks de uso no mesmo stream.** Se um chunk de uso anterior atribuiu `"X"` e o último ecoa o modelo pedido, o último evento chega com `ResolvedModel == ""` e o `mergeUsageSnapshot` mantém `"X"`. É um limite conhecido e aceito: os provedores OpenAI-compatíveis mandam um só chunk de uso (`stream_options.include_usage`), e o Codex, um só terminal.
- **Sessões antigas do fork.** Builds do fork com o patch atual gravaram `resolvedModel` cru e também igual ao pedido. O relatório limpa e compara na leitura (D2.1-21, D2.1-22, A2.1-14); o arquivo não é reescrito.
- **Agregação depois do `continue` do preço.** É o erro mais provável da exibição: um roteador sem preço no registro (`router/auto`) some do relatório. D2.1-20 pega isso.
- **Modelo pedido na leitura.** O relatório compara com `payload.model` ou, sem ele, com o `ModelID` da sessão. No `zero exec`, o `ModelID` é o mesmo `resolved.Provider.Model` que vai ao provedor (`internal/cli/exec.go`, conferido); na TUI ele vem de `m.modelName` (não conferido). Se a TUI trocar de modelo no meio da sessão sem escalonamento, um evento antigo do fork com valor igual ao modelo novo apareceria como "diferente". Só afeta sessões gravadas por builds antigos do fork, porque os eventos novos já chegam filtrados pelo provedor; é aceito.
- **Leitura por posição no texto.** Com atribuição, o texto ganha linhas entre `total` e `net LOC`. Quem processa o relatório deve usar `--json`.
- **ESC cru no JSON.** Um gateway que mande um byte de controle cru dentro da string JSON faz o chunk inteiro falhar no `json.Unmarshal`, como hoje; isso não muda nesta tarefa.
- **Hermeticidade.** D2.1-18 e D2.1-19 tocam sessões: diretórios só em `t.TempDir()`; nada no `HOME` real.

## Decisões

- **D-2.1-a. Lista de permissão com `unicode.IsPrint`, em vez de remover só `Cc` e `Cf`.** Cobre o que o mantenedor pediu e também `U+2028`/`U+2029`, espaços não ASCII, uso privado e não atribuídos, que não têm lugar num id de modelo. Uma função da biblioteca padrão, sem tabela própria para manter. Conferido com go1.27.2 (o `go.mod` pede go 1.26.11; D2.1-2 e D2.1-3 confirmam na versão do módulo): `IsPrint` é falso para ESC, NUL, DEL, `U+0085`, `U+009B`, `U+202E`, `U+2066`, `U+200B`, `U+200D`, `U+FEFF`, `U+00AD`, `U+2028`, `U+00A0`, `U+3000` e `U+E000`, e verdadeiro para `U+FFFD` e o espaço ASCII.
- **D-2.1-b. Limite de 256 bytes, corte na fronteira de runa, sem marcador.** "Algumas centenas de bytes" na palavra do mantenedor; um ARN de perfil de inferência do Bedrock tem cerca de 100. Um marcador de corte somaria bytes e poderia ser lido como parte do id.
- **D-2.1-c. A mesma limpeza nos dois lados antes de comparar; igualdade exata de bytes.** Segue "normalize before matching" do `AGENTS.md` e evita que um pedido longo (mais de 256 bytes) ecoado igual seja gravado truncado como "outro modelo".
- **D-2.1-d. Comparação no provedor, limpeza também no gravador e na leitura.** Só o provedor conhece o modelo pedido no fio; o `EventUsagePayload` é o único gravador e limpa de novo por defesa. Revisto em 2026-11-16: com R10, o `BuildReport` lê a chave e passa por `ResolvedModelAttribution` de novo, porque o arquivo pode vir de um build antigo do fork (cru ou igual ao pedido).
- **D-2.1-h. Bloco separado no relatório, não coluna.** A tabela por dia fica como está; o bloco `resolved models` e a chave `resolvedModels` (fora de `total` e `buckets`) só existem quando há atribuição. Evita coluna vazia, mantém a saída de hoje byte a byte sem atribuição e deixa os consumidores do JSON compatíveis (chave aditiva). Os números vêm antes e o texto não confiável por último, sem preenchimento.
- **D-2.1-i. A exibição é um commit único, separado e por último.** Decisão do operador (2026-11-16): se o mantenedor recusar a exibição, ela sai sem tocar na gravação. Por isso os testes dela vão no mesmo commit, e não no par `test:`/`feat:`; a prova de que falham sem a limpeza vai na PR.
- **D-2.1-e. As funções ficam em `internal/zeroruntime`.** É o pacote neutro que provedores e `internal/usage` já importam; um pacote novo seria peso sem ganho. O `internal/redaction` tem uma limpeza parecida, mas não exportada e com outro fim (segredos).
- **D-2.1-f. O estado do stream guarda o último valor não vazio já limpo.** Um `model` que fica vazio depois da limpeza não apaga um valor válido anterior; a comparação com o pedido acontece só na emissão do uso.
- **D-2.1-g. Por causa do JSON**, os testes de controle C0 usam escapes JSON no SSE; os de C1 e de formato usam escape e UTF-8 cru. Conferido com go1.27.2: o `encoding/json` rejeita controle cru em string, decodifica `\u001b` e `\u0000` para os bytes de controle, troca UTF-8 inválido por `U+FFFD` e, ao gravar, escapa C0 e `U+2028` mas grava C1 e `U+202E` crus, o que deixaria o `events.jsonl` sujo sem a limpeza.
